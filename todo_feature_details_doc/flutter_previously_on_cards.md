# Feature Implementation Spec: Previously-On Cards

## 1. Feature Overview
**Target Application:** Flutter Client (`lib/`)  
**Objective:** Insert lightweight recap cards at the right moments so users can re-enter a story without needing perfect memory.

This is distinct from Catch-Up Capsule:
- Catch-Up Capsule appears after absence.
- Previously-On Cards appear inline before important new beats.

## 2. Why This Matters
- Real-time stories punish imperfect memory.
- Users should not need to mentally reconstruct multiple prior artifacts.
- Inline recaps reduce friction without requiring a separate recap flow.

## 3. Product Behavior
Before a major unlock or after a long silence, show a compact recap card in the timeline:
- "Previously on..."
- 1-2 lines summarizing the latest important context
- one CTA to revisit the most relevant earlier artifact

## 4. Trigger Conditions
Insert a Previously-On card when any of these are true:
- new artifact arrives after `12+ hours` gap
- content type shifts dramatically, e.g. chat -> phone call -> voice note
- first unlock of a new story day
- user has not opened the app in `6+ hours`

## 5. Card Content
Each card should contain:
- label: `PREVIOUSLY ON`
- one sentence summary
- optional linked artifact reference:
  - `Reopen the receipt`
  - `Review the last call`
- optional tension question:
  - `Did Mira lie about where she went?`

## 6. Phase 1 Implementation
Generate the card client-side using recent unlocked artifacts.

Do not store these as Firestore documents yet.
Instead, create synthetic timeline items at render time.

## 7. Data Model
Create a synthetic timeline model:
```dart
class TimelineFeedEntry {
  final StoryItem? item;
  final PreviouslyOnCardData? recap;
  final bool isSynthetic;
}
```

Suggested recap model:
```dart
class PreviouslyOnCardData {
  final String id;
  final String summary;
  final String? linkedItemId;
  final String? linkedItemType;
  final String? tensionQuestion;
  final DateTime insertedAt;
}
```

## 8. Provider Changes
Current timeline provider returns `List<StoryItem>`.
This feature will be easier if we introduce a presentation-layer provider that maps story items into renderable feed entries.

Suggested:
- leave `timelineFeedProvider` intact
- add `timelinePresentationProvider`

## 9. UI Requirements
New widget:
- `lib/widgets/previously_on_card.dart`

Design:
- different from regular artifacts
- editorial / briefing card feel
- compact enough not to feel like filler

Required actions:
- `Review`
- `Dismiss`

## 10. Summary Heuristics
Look back over the last 3-5 important unlocked artifacts.

Prefer:
- the last receipt if it changed stakes
- the latest phone call if conflict increased
- the latest journal if it includes intent/fear/confession

Summary templates:
- "After the suspicious late-night receipt, X denied everything in chat."
- "The last time we heard from X, they were hiding something from Y."
- "The investigation escalated after the voice note implicated Z."

## 11. Implementation Steps
1. Create recap model and timeline presentation model.
2. Add heuristic builder for recap card insertion.
3. Build new recap widget.
4. Update timeline list renderer to support mixed entry types.
5. Add navigation to reopen linked items.
6. Persist dismissals locally for current story session if needed.

## 12. Acceptance Criteria
- Timeline can render a mix of real artifacts and synthetic recap cards.
- Cards appear only when trigger conditions are met.
- Cards never break sort order.
- Review action opens a valid previous artifact.

## 13. Testing & Verification
- Unit test insertion rules.
- Verify card placement around day changes and long gaps.
- Verify no duplicate recap cards on repeated rebuilds.
- Verify dismissing a card hides it for the current session.

## 14. Future Enhancements
- admin-authored recap cards
- voice recap player
- recap cards generated by backend critic system
